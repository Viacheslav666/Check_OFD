# Требования: доля маркированных чеков по торговым точкам

**Источник:** ТЗ v1.1 от 24.11.2026 (ОФД.ру / ФФД 1.2).  
**Стек (зафиксирован заказчиком):** Java 21 LTS, Spring Boot (Windows Service / WinSW), PostgreSQL + Flyway, JavaFX desktop (MSI / jpackage).  
**Отложено:** Matrix, Zabbix.

## 1. Цель

Сервис на Windows Server собирает **все типы чеков** из официального API ОФД.ру, сохраняет в PostgreSQL и считает долю чеков с маркированными товарами по торговым точкам (ТТ). Desktop-клиент показывает рейтинг «худших» ТТ, статистику по товарным группам, матрицу ТТ×группа, поиск чеков с детализацией позиций и выгрузку в Excel.

## 2. Масштаб и инфраструктура

| Параметр | Значение |
|---|---|
| ТТ | ~150 |
| Чеков/сутки | 1000–2000 |
| Пользователи | 2 |
| Сервер | Windows Server x64, 2× Xeon E5-2680 v4, 24 GB RAM |

## 3. User stories и критерии приёмки

### US-01. Сбор чеков из ОФД

**Как** оператор системы, **я хочу**, чтобы сервис автоматически загружал чеки из ОФД.ру, **чтобы** аналитика строилась на актуальных данных.

**Acceptance criteria**

- [ ] AC-01.1 Используется метод `receipts-info` (раздел 2.10.1 API ОФД v1.75).
- [ ] AC-01.2 Список ККТ берётся из API (раздел 3.2 / информация о ККТ).
- [ ] AC-01.3 Авторизация: `AuthToken={API KEY}` (выдаётся в ЛК: Настройки → Управление передачей данных).
- [ ] AC-01.4 Соблюдается лимит: **не чаще 1 запроса в 2 секунды** к `receipts-info`.
- [ ] AC-01.5 Один запрос покрывает период **≤ 30 суток**; глубина истории **до 90 суток**.
- [ ] AC-01.6 Поддерживаются все типы ФД из ответа (`Tag` 3/31/4/41 — чек, чек коррекции, БСО, БСО коррекции).
- [ ] AC-01.7 Первичная загрузка — последние 90 дней (окнами по ≤30 дней); далее — инкрементальная по курсору.
- [ ] AC-01.8 Повтор при HTTP 429 и 5xx с backoff; при 400/403/404 — без бессмысленного retry.
- [ ] AC-01.9 Режим `mock` работает без реального API KEY и наполняет БД реалистичными ФФД 1.2 чеками.

### US-02. Определение маркированного чека (ФФД 1.2)

**Как** аналитик, **я хочу**, чтобы чек считался маркированным по правилам ФФД 1.2, **чтобы** метрики были сопоставимы с требованиями маркировки.

**Acceptance criteria**

- [ ] AC-02.1 Чек **маркированный**, если **хотя бы одна** позиция удовлетворяет:  
  - в позиции есть код маркировки (тег **1163** / `ProductCode` с непустым значением), **и/или**  
  - тег **1212** (`SubjectType`) равен **31** или **33**.
- [ ] AC-02.2 Пустой объект `ProductCode: {}` **не** считается наличием кода маркировки.
- [ ] AC-02.3 Признак сохраняется на уровне чека (`has_marked_goods`) и позиций (`is_marked`).

### US-03. Торговые точки

**Как** руководитель сети, **я хочу** видеть метрики по ТТ, **чтобы** находить проблемные точки.

**Acceptance criteria**

- [ ] AC-03.1 ТТ формируется из адреса установки ККТ и места расчётов (`FiscalAddress` + `FiscalPlace` / аналоги в чеке).
- [ ] AC-03.2 Несколько ККТ с одинаковым ключом адреса+места относятся к одной ТТ.
- [ ] AC-03.3 Доля маркированных = `marked_receipts / total_receipts * 100` за выбранный период.

### US-04. Дашборд и рейтинг «худших» ТТ

**Как** пользователь клиента, **я хочу** видеть % по ТТ и рейтинг худших, **чтобы** быстро реагировать.

**Acceptance criteria**

- [ ] AC-04.1 Экран дашборда: список ТТ с %, числом чеков, числом маркированных.
- [ ] AC-04.2 Рейтинг худших: ТТ с долей **ниже** настраиваемого порога (по умолчанию **25%**), сортировка по возрастанию %.
- [ ] AC-04.3 Порог хранится в настройках и меняется в UI без пересборки.

### US-05. Товарные группы и номенклатура

**Как** аналитик, **я хочу** статистику по группам товаров, **чтобы** понимать структуру маркировки.

**Группы (фиксированный справочник):** бакалея, табак, никотинсодержащая, пиво, разливное пиво, вода, молочка, соки (+ «прочее»).

**Acceptance criteria**

- [ ] AC-05.1 Справочник номенклатуры строится **правилами** по наименованиям позиций чеков (keywords / regex).
- [ ] AC-05.2 Экран статистики по группам: число позиций, число маркированных, доля.
- [ ] AC-05.3 Матрица ТТ × группа с долями / количествами.
- [ ] AC-05.4 Правила редактируемы через настройки/БД (seed + CRUD API).

### US-06. Поиск чеков и детализация

**Как** пользователь, **я хочу** искать чеки и смотреть позиции, **чтобы** проверять спорные случаи.

**Acceptance criteria**

- [ ] AC-06.1 Фильтры: период, ТТ, ККТ, «только с маркировкой», группа, текст наименования.
- [ ] AC-06.2 Карточка чека: реквизиты ФД + список позиций (имя, цена, кол-во, SubjectType, ProductCode, is_marked).
- [ ] AC-06.3 Пагинация списка чеков.

### US-07. Excel-экспорт

**Как** пользователь, **я хочу** выгрузить отчёт в Excel, **чтобы** передать в бухгалтерию/контроль.

**Acceptance criteria**

- [ ] AC-07.1 Экспорт текущего представления (дашборд ТТ / группы / матрица / чеки) в `.xlsx`.
- [ ] AC-07.2 Кодировка и числа корректны в Excel (кириллица, проценты).

### US-08. Установка и безопасность

**Как** админ сервера, **я хочу** установить сервис и клиент по инструкции, **чтобы** запустить систему в проде.

**Acceptance criteria**

- [ ] AC-08.1 Backend — Windows Service через WinSW; конфиг в репозитории.
- [ ] AC-08.2 API KEY хранится вне VCS (env / encrypted config), не пишется в логи.
- [ ] AC-08.3 Клиент — MSI (jpackage); README на русском с шагами PostgreSQL / service / API KEY / MSI.
- [ ] AC-08.4 Demo/mock mode без реального ключа.

## 4. Нефункциональные требования

- Логирование: структурированные логи (уровень INFO/WARN/ERROR), без секретов.
- Идемпотентность загрузки: уникальный ключ чека (`DocRawId` / `Id`).
- REST API для desktop-клиента (локальная сеть, базовый API-key клиента опционально в настройках).
- CI: сборка + unit + integration + e2e collection→metrics; все тесты зелёные.

## 5. Открытые вопросы ТЗ («Требует проверки») и проектные решения

| # | Вопрос | Решение в продукте |
|---|---|---|
| Q1 | Есть ли пагинация у `receipts-info`? | В док. v1.75 пагинации нет — возвращается массив `Data`. Клиент терпим к неожиданным полям (`@JsonIgnoreProperties`). Если ответ обрезан — логируем WARN; конфиг `ofd.max-receipts-warn`. |
| Q2 | По какому полю фильтровать период: `DocDateTime` или `CDateUtc`? | По умолчанию фильтр запроса к ОФД — как в API (`dateFrom`/`dateTo`). В БД храним оба; **метрики и UI-фильтры** — по `DocDateTime` (локальное время кассы). Переключатель `ofd.filter-time-field=DOC_DATE_TIME\|C_DATE_UTC`. |
| Q3 | 12-значный ИНН ИП | Path-параметр `INN` — строка; принимаем 10 и 12 цифр без обрезания. Валидация: `^\d{10}(\d{2})?$`. |
| Q4 | Возвращает ли `receipts-info` **все** чеки или только с маркировкой? | Название метода «с кодами маркировки», но пример в док. содержит позиции **без** кода. **Assumption (изолировано в mapping):** метод возвращает все чеки периода с деталями; маркировка определяется локально. Конфиг `ofd.assume-receipts-info-all=true`. Если окажется иначе — fallback на `receipts` + `receipt/{RawId}` (заготовка интерфейса). |

Все допущения живут **только** в слое `ofd.mapping` / `OfdProperties` — домен не знает «сырых» имён полей ОФД.
